# طراحی فنی اولیه

## پشته پیشنهادی
Python 3.12، aiogram 3، SQLite با aiosqlite، zoneinfo و کتابخانه سبک تاریخ شمسی؛ Docker برای اجرا و pytest برای آزمون. SQLite برای یک نمونه و حجم کم مناسب است؛ در صورت مقیاس‌پذیری یا چند نمونه، PostgreSQL و سازوکار صف/قفل توزیع‌شده بررسی می‌شود. کتابخانه jdatetime برای تبدیل تاریخ شمسی استفاده می‌شود.

## مرزبندی
- لایه Telegram: دریافت پیام، فرمان و تعامل مرحله‌ای؛ فقط چت خصوصی.
- لایه کاربرد: اعتبارسنجی، مجوز مالکیت، ثبت، ویرایش، حذف و مدیریت تکرار.
- لایه زمان: استخراج محدود متن، تبدیل شمسی، منطقه زمانی و بررسی ابهام DST؛ قواعد زمان و خطاها با تست پوشش داده می‌شوند.
- لایه ذخیره‌سازی: کاربران، یادآوری‌ها، زمان‌بندی و تلاش‌های ارسال؛ مهاجرت افزایشی ستون‌ها از نمونه قبلی.
- کارگر ارسال: واکشی وظایف سررسیدشده، تلاش مجدد با backoff، گزارش خطا و بازیابی پس از ری‌استارت.

## داده و تضمین ارسال
زمان سررسید یک‌باره به UTC ذخیره شود. برای تکراری، قاعده، ساعت محلی و نام منطقه زمانی جداگانه ذخیره شود. تراکنش‌های دیتابیس مالکیت و وضعیت را بررسی کنند. تلگرام و دیتابیس تراکنش مشترک ندارند؛ پس تضمین exactly-once ممکن نیست: در قطع شدن بین ارسال و ثبت موفقیت ممکن است پیام تکراری شود. تلاش مجدد باید محدود و با backoff باشد؛ خطاهای دائمی مانند مسدودشدن ربات نباید بی‌پایان تکرار شوند. صرف پاسخ موفق API تضمین دیده‌شدن پیام نیست.

## امنیت و عملیات
توکن فقط از محیط، بدون commit؛ دسترسی دیتابیس محدود؛ پیام و توکن در لاگ نیاید؛ ورودی‌ها محدود و معتبر شوند. پشتیبان‌گیری سازگار با SQLite و بررسی بازیابی مستند شود. اجرای تنها یک worker در نسخه SQLite الزامی است. حجم پروژه کم نگه داشته شود؛ محیط مجازی، کش، دیتابیس و خروجی‌های تولیدی در مخزن و بسته تحویل قرار نگیرند.

## محدودیت‌های عملیاتی
یک نمونه ربات و worker اجرا شود. زمان‌بندی تکراری از زمان محلی ذخیره‌شده استفاده می‌کند؛ نمونه اولیه برای مقیاس بالا یا تضمین ارسال دقیقاً یک‌بار طراحی نشده است. جزئیات پشتیبان‌گیری و تلاش مجدد در README آمده است.
